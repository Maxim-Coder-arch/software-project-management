## 1. Методика оценки

Показатель риска:

```
R = P × I
```

где **P** — вероятность наступления, **I** — влияние на проект.

### 1.1. Шкала вероятности (P)

| Балл | Оценка | Описание |
|:---:|---|---|
| 1 | Очень низкая | Практически не случается, меньше 10 % |
| 2 | Низкая | Возможно, но маловероятно, 10–30 % |
| 3 | Средняя | Может случиться, 30–50 % |
| 4 | Высокая | Скорее всего случится, 50–80 % |
| 5 | Очень высокая | Случится почти наверняка, больше 80 % |

### 1.2. Шкала влияния (I)

| Балл | Оценка | Последствия |
|:---:|---|---|
| 1 | Незначительное | Не влияет на сроки и результат |
| 2 | Малое | Задержка до 1–2 дней, исправляется в рамках итерации |
| 3 | Среднее | Задержка до недели, часть функций урезается |
| 4 | Серьёзное | Срыв итерации, потеря ключевой функции |
| 5 | Критическое | Срыв сдачи проекта или невозможность продолжать |

### 1.3. Приоритет по значению R

| Значение R | Приоритет | Реакция |
|:---:|---|---|
| 20–25 | **Критический** | Меры начинаются немедленно, контроль каждый день |
| 12–19 | **Высокий** | План мер в течение недели, контроль на каждой итерации |
| 6–11 | **Средний** | Наблюдение, меры по срабатыванию признака |
| 1–5 | **Низкий** | Только учёт в реестре |

## 4. Три критических риска

Выбраны три риска с наибольшим значением R: **R01 (20), R02 (20) и R03 (16)**.

R01 и R02 имеют одинаковое значение. Третьим по величине идёт R03 (16), следующий за ним R04 (15).

---

### 4.1. R01. Неполные и меняющиеся требования (R = 20)

**Почему опаснее остальных**

Это риск с самым высоким влиянием (5) при высокой вероятности (4). Он действует на проект целиком и порождает остальные: чем больше изменений, тем сильнее недооценка сроков (R02), тем чаще переделывается база данных (R05) и интерфейс (R09). Остальные риски затрагивают отдельные участки, а этот влияет на всё сразу.

**Какие задачи затрагивает**

| Задача | Как затрагивается |
|---|---|
| Проектирование базы данных | Новые поля и связи ломают уже созданную структуру |
| Контракт API | Меняются методы и форматы, нужно переписывать обе стороны |
| Макеты и интерфейс | Переделка экранов, уже сданных дизайнером и Frontend |
| Тест-кейсы | Устаревают и переписываются |
| План итераций | Постоянное смещение объёма |

**Последствия, если ничего не предпринимать**

- Объём работ растёт без роста сроков, команда не успевает.
- Результат итерации превращается в набор недоделанных функций.
- Растёт число конфликтов: «вы просили иначе» против «мы так не договаривались».
- К сдаче проекта нет ни согласованных требований, ни работающих функций.

**Меры**

| Мера | Срок |
|---|---|
| Зафиксировать требования первой итерации письменно, с подписью заказчика | До начала итерации 1 |
| Ввести правило: изменения принимаются только в начале итерации, а не в её середине | Сразу |
| Вести журнал запросов на изменения с оценкой влияния на сроки | Постоянно |
| Каждое новое требование сопровождается решением: добавляем с переносом чего-то другого или откладываем | При каждом запросе |

**Признак срабатывания:** больше двух запросов на изменение за итерацию.

---

### 4.2. R02. Недооценка трудоёмкости (R = 20)

**Почему опаснее остальных**

Это единственный риск с вероятностью 5: он практически неизбежен, потому что у команды нет опыта точной оценки на подобных проектах. Он также самый «тихий»: проявляется не одним событием, а накоплением мелких задержек, которые замечают слишком поздно.

**Какие задачи затрагивает**

| Задача | Как затрагивается |
|---|---|
| Все задачи итераций | Каждая занимает больше запланированного |
| Интеграция Frontend и Backend | Происходит в самом конце, куда накапливаются задержки |
| Тестирование | Время сжимается, проверка сокращается |
| Документация и демонстрация | Остаются без времени, их делают в последний день |

**Последствия, если ничего не предпринимать**

- Итерации не закрываются в срок, хвосты переходят в следующую.
- К четвёртой итерации накапливается долг, который невозможно погасить.
- Первыми жертвами становятся тестирование и документация, то есть то, что защищает качество.
- Команда выходит на сдачу с неготовой частью функций или с неподготовленной демонстрацией.

**Меры**

| Мера | Срок |
|---|---|
| Закладывать резерв 20 % времени в каждую итерацию, не планировать 100 % доступных часов | При планировании |
| Разбивать задачи на части не более 8 часов: крупные задачи оцениваются хуже | При планировании |
| Сравнивать план и факт каждую неделю, корректировать оценку следующей итерации | Еженедельно |
| Заранее определить, что отложить в случае отставания (список «может подождать») | До начала итерации 1 |

**Признак срабатывания:** отставание от плана больше 15 % к середине итерации.

---

### 4.3. R03. Блокировка Frontend отсутствием API (R = 16)

**Почему опаснее остальных**

Это риск с прямой цепочкой зависимости: Frontend нельзя продолжать без API, а API зависит от базы данных. Задержка у одного участника мгновенно останавливает другого, и потерянные часы невосполнимы. Кроме того, он усиливается рисками R02 и R05: любая задержка Backend немедленно превращается в простой Frontend.

**Какие задачи затрагивает**

| Задача | Как затрагивается |
|---|---|
| Экраны заявителя, специалиста, администратора | Не могут быть подключены к данным |
| Тестирование интерфейса | Нечего проверять |
| Демонстрация сквозного сценария | Не собирается без реальных данных |

**Последствия, если ничего не предпринимать**

- Frontend простаивает или тратит время на переделки, когда API наконец появляется в другом виде.
- Интеграция откладывается на последние дни, и ошибки находятся там, где исправлять их дороже всего.
- Растёт напряжение между Frontend и Backend: каждый считает виноватым другого.

**Меры**

| Мера | Срок |
|---|---|
| Согласовать контракт API письменно в первые два дня каждой итерации | Начало итерации |
| Поднять заглушку (mock-сервер) по контракту, чтобы Frontend работал без ожидания | В течение 2–3 дней после согласования |
| Backend реализует методы в порядке, нужном Frontend, а не в удобном самому | Постоянно |
| Ежедневная выкладка сборки, чтобы подмена заглушки на реальный API проходила постепенно | Ежедневно |

**Признак срабатывания:** Frontend простаивает более 4 часов подряд.

## 6. Как реестр будет вестись дальше

### 6.1. Периодичность

| Мероприятие | Когда | Что делается |
|---|---|---|
| Просмотр критических и высоких рисков | Еженедельно | Проверка признаков срабатывания, обновление оценок |
| Полный пересмотр реестра | В конце каждой итерации | Переоценка P и I, закрытие устаревших рисков, добавление новых |
| Немедленный пересмотр | При наступлении риска | Запись факта, оценка последствий, корректировка плана |

### 6.2. Правила

- У каждого риска один ответственный. Он следит за признаками срабатывания и сообщает руководителю.
- Оценка пересматривается после каждой итерации: вероятность R02 должна падать по мере накопления опыта, а вероятность R08 растёт ближе к сдаче.
- Риск, который наступил, переходит из реестра рисков в список проблем, а в реестр добавляется запись о принятых мерах.
- Новые риски добавляются в любой момент, любым участником.

### 6.3. Формат записи об изменении

| Дата | ID | Было (P × I) | Стало (P × I) | Причина |
|---|:---:|:---:|:---:|---|
| ГГ-ММ-ДД | R00 | 0 × 0 | 0 × 0 | Что изменилось |

## 7. Итог

- Составлен реестр из десяти рисков с оценкой по шкале 1–5 и расчётом R = P × I.
- Два риска имеют критический приоритет (R01, R02), пять высокий, три средний.
- Три наиболее опасных риска: **неполные и меняющиеся требования (20)**, **недооценка трудоёмкости (20)** и **блокировка Frontend отсутствием API (16)**.
- Первые два связаны между собой: меняющиеся требования увеличивают трудоёмкость. Поэтому работа над требованиями (фиксация, правило приёма изменений) даёт эффект сразу по обоим рискам.
- Третий риск устраняется организационно: контракт API и mock-сервер убирают зависимость вместо ожидания.
- Для каждого риска назначен ответственный, определены признаки срабатывания и меры.
