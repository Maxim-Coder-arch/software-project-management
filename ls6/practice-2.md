## 1. Исходная ситуация

В ходе контрольной проверки выявлено шесть обстоятельств:

| № | Обстоятельство |
|:---:|---|
| 1 | Backend-разработчик отстаёт от графика на три дня |
| 2 | Frontend-разработчик завершил интерфейс, но не может подключить его к API |
| 3 | Тестировщик не получил готовую сборку |
| 4 | Заказчик попросил добавить экспорт расписания в PDF |
| 5 | Разработчик базы данных обнаружил ошибку в структуре хранения расписания |
| 6 | Резервное копирование базы данных не настроено |

**Состав команды** (по ролям): руководитель проекта, аналитик, Backend-разработчик, разработчик базы данных, Frontend-разработчик, тестировщик. Если Backend и разработчик БД это один человек, план остаётся рабочим, но порядок задач в днях 1–3 строго последовательный (см. раздел 7).

## 2. Проблемы и риски

### 2.1. Критерий разделения

- **Проблема** это событие, которое уже произошло и уже мешает работе.
- **Риск** это событие, которое пока не произошло, но может произойти и нанести ущерб.

### 2.2. Классификация

| № | Обстоятельство | Группа | Обоснование |
|:---:|---|---|---|
| 1 | Backend отстаёт на 3 дня | **Проблема** | Отставание зафиксировано, срок уже сдвинут |
| 2 | Frontend не может подключить интерфейс к API | **Проблема** | Работа остановлена прямо сейчас |
| 3 | Тестировщик без сборки | **Проблема** | Простой тестирования уже идёт |
| 5 | Ошибка в структуре хранения расписания | **Проблема** | Дефект найден и существует в проекте |
| 4 | Новая функция: экспорт в PDF | **Риск** | Запрос ещё не принят. Если принять без пересмотра плана, сорвёт сроки |
| 6 | Нет резервного копирования | **Риск** | Потери данных ещё не было, но условия для неё созданы |

> Обстоятельство 6 это уязвимость, а не событие: пока ничего не сломалось, она не заметна. Именно поэтому её нельзя оставлять «на потом». Исправление ошибки в БД (п. 5) создаёт условия, при которых этот риск может превратиться в проблему.

### 2.3. Связь между обстоятельствами

Обстоятельства не независимы. Они образуют цепочку:

```
Ошибка в структуре БД (5) ──> API нельзя завершить (1) ──> Frontend не подключить (2)
                                                      └──> Нет сборки для проверки (3)

Исправление БД (5) без резервной копии (6) ──> риск потери данных
Новая функция (4) ──> дополнительная нагрузка на уже отстающего Backend (1)
```

Корень цепочки: **ошибка в БД и отставание Backend**. Три из четырёх проблем (2, 3 и частично 1) являются их следствием, а не самостоятельными событиями. Поэтому лечить нужно причину, а не каждое проявление отдельно.

## 3. Что произойдёт дальше, если ничего не менять

| Событие | Вероятный срок | Последствие |
|---|---|---|
| Backend пишет API поверх неверной структуры БД | Дни 1–4 | Переделка уже написанного после исправления структуры, отставание растёт с 3 до 5–6 дней |
| Frontend продолжает ждать | Дни 1–5 | Либо простой, либо переписывание под API, который появится в другом виде |
| Интеграция Frontend и Backend откладывается в конец | Дни 7–10 | Ошибки интеграции находятся за 2–3 дня до показа, исправить их некогда |
| Тестировщик получает первую сборку в последние дни | Дни 8–10 | Дефекты найдены, но не исправлены; демонстрация идёт с известными ошибками |
| Заказчик получает «да» на PDF без изменения плана | День 1 | Нагрузка на Backend растёт, а ожидания заказчика не соответствуют реальности |
| Миграция структуры БД выполняется без резервной копии | Дни 2–5 | Любая ошибка скрипта приводит к потере данных, восстановление невозможно |
| Накопленные задержки совпадают | День 8–10 | Демонстрация сорвана или проведена на урезанной версии без предупреждения заказчика |

**Вывод.** Если действовать по старому плану, то при наложении всех факторов проект демонстрируется неработающим. Поэтому нужны изменения в последовательности работ и объёме, а не просьба «работать быстрее».

## 4. Принципы реагирования

1. **Сначала защита, потом ремонт.** Прежде чем менять структуру БД, создаём резервное копирование. Это занимает часы, а риск потери данных стоит дней.
2. **Сначала причина, потом следствия.** Исправляем структуру БД до того, как Backend продолжит писать API. Иначе работа будет выполнена дважды.
3. **Убираем зависимость, а не ускоряем поставщика.** Frontend и тестировщик переключаются на заглушку (mock) по согласованному контракту API и перестают ждать.
4. **Вертикальные срезы вместо «готовности по слоям».** Backend отдаёт методы не все сразу, а по одному сценарию: сначала просмотр расписания, затем редактирование. Каждый готовый срез сразу идёт в интеграцию и на проверку.
5. **Сокращаем объём, а не сроки.** Новая функция и всё, что не входит в демонстрационный сценарий, уходят из текущего плана.
6. **Никаких сверхурочных как основного плана.** Резерв нужен на непредвиденное, а не на закрытие запланированного отставания.

## 5. План реагирования по каждому обстоятельству

### 5.1. Backend отстаёт на три дня (проблема)

**Решение:** сократить объём и поменять порядок, а не добавлять часы.

| Действие | Эффект |
|---|---|
| Определить **демонстрационный сценарий** (просмотр расписания группы и преподавателя, создание и редактирование занятия, фильтрация) | Всё остальное уходит из плана на 10 дней |
| Реализовывать методы API в порядке сценария, **вертикальными срезами**: чтение, затем изменение, затем удаление | Frontend и тестировщик получают работающую часть раньше, а не всё сразу в конце |
| Убрать с Backend несрочные задачи: отчёты, вспомогательные справочники, настройки администратора | Ориентировочно 2 рабочих дня высвобождается |
| Передать разработчику БД часть подготовительной работы (скрипты, тестовые данные), если роли разделены | Ориентировочно 1 рабочий день высвобождается |

**Расчёт восстановления графика (оценка):**

```
Отставание:                          3 дня
Сокращение объёма вне сценария:     −2 дня
Передача подготовительных работ:    −1 день
Остаток отставания:                  0 дней, резерв нет
```

Резерва нет, поэтому критична контрольная точка дня 5 (см. раздел 8) и правило заморозки с дня 8.

---

### 5.2. Frontend не может подключить интерфейс к API (проблема)

**Решение:** разорвать зависимость через mock API и контракт.

| Действие | Ответственный | Срок |
|---|---|---|
| Аналитик фиксирует контракт API (методы, форматы запросов и ответов, коды ошибок) по демонстрационному сценарию | Аналитик | День 1 |
| Подписание контракта Backend и Frontend (30–60 минут) | Backend, Frontend | День 1 |
| Поднять mock-сервер по контракту | Тестировщик (с Frontend) | День 2 |
| Frontend подключает интерфейс к mock и проверяет все состояния: данные, пусто, ошибка, загрузка | Frontend | Дни 2–4 |
| Подмена mock на реальные методы по мере готовности срезов | Frontend, Backend | С дня 4 |

**Что даёт это решение:** интерфейс, который «завершён, но не работает», перестаёт простаивать: его проверяют, дорабатывают состояния ошибок и готовят к реальным данным.

---

### 5.3. Тестировщик не получил готовую сборку (проблема)

**Решение:** передавать промежуточные сборки, не дожидаясь «готового» продукта.

| Действие | Срок |
|---|---|
| С дня 2 тестировщик работает с mock: составляет тест-кейсы демонстрационного сценария, пишет тесты API по контракту | Дни 2–3 |
| Первая промежуточная сборка (только чтение расписания) передаётся тестировщику | День 4 |
| Далее ежедневная выкладка сборки до 16:00, даже если она неполная | С дня 4 |
| Тестировщик возвращает результат в тот же день или на следующий | Постоянно |
| Тестировщик помогает с подготовкой тестовых данных для проверки миграции БД | Дни 2–3 |

**Принцип:** неполная сборка с известными ограничениями полезнее, чем идеальная сборка, которая не появится.

---

### 5.4. Заказчик просит экспорт расписания в PDF (риск)

**Решение:** не принимать в текущий объём автоматически, а предложить заказчику выбор.

| Вариант | Трудоёмкость (оценка) | Влияние на сроки |
|---|---|---|
| **А.** Полноценный экспорт в PDF на сервере | 12–16 ч | Сорвёт демонстрацию при текущем отставании |
| **Б.** Облегчённая печатная форма (страница расписания, оптимизированная для печати; сохранение в PDF средствами браузера) | 2–4 ч, Frontend | Допустимо при выполнении условий |
| **В.** Перенос в следующую версию с фиксацией в бэклоге | 0 ч сейчас | Не влияет на сроки |

**Решение руководителя:**

1. Вариант А **исключается** из текущего плана.
2. Заказчику предлагается вариант **В** с фиксацией в бэклоге как основной.
3. Вариант **Б** реализуется **только если** на день 7 выполнены условия: контрольная точка дня 5 пройдена, критичные дефекты закрыты, у Frontend есть свободное время. Если условия не выполнены, вариант Б тоже переносится.

**Что ответить заказчику (краткая форма):**

> Экспорт в PDF принят в бэклог как отдельная функция следующей версии. В текущий срок включить полноценный экспорт нельзя без риска для основного сценария. Если к 7-му рабочему дню запас времени позволит, покажем облегчённый вариант: страницу расписания в виде, удобном для печати и сохранения в PDF.

**Принцип:** любое изменение объёма принимается вместе с решением, что убирается или переносится взамен. Если ничего не убирается, срок не меняется только на бумаге.

### 5.5. Ошибка в структуре хранения расписания (проблема)

**Решение:** исправлять сразу, но безопасно и с ограничением по времени.

**Почему нельзя отложить.** Расписание это основной объект системы. Ошибка в его структуре затрагивает все методы чтения и изменения. Чем позже она исправляется, тем больше кода и данных придётся переделывать.

**Порядок действий:**

| Шаг | Действие | Ответственный | Срок |
|:---:|---|---|---|
| 1 | Создать резервную копию текущей БД и проверить восстановление (см. п. 5.6) | Разработчик БД | День 1, до любых изменений |
| 2 | Описать ошибку: что хранится неверно, какие данные и методы затронуты | Разработчик БД, аналитик | День 1 |
| 3 | Определить минимальное исправление: только то, что нужно для демонстрационного сценария | Разработчик БД, Backend | День 1 |
| 4 | Написать скрипт миграции, прогнать на копии БД | Разработчик БД | День 2 |
| 5 | Проверить данные после миграции (количество записей, целостность, примеры) | Тестировщик | День 2 |
| 6 | Применить миграцию к рабочей БД | Разработчик БД | Конец дня 2 |
| 7 | Backend продолжает API на исправленной структуре | Backend | С дня 3 |

**Ограничение времени (time-box).** На исправление отводятся 2 дня. Если к концу дня 2 миграция не прошла проверку, руководитель принимает решение: упростить структуру или оставить временное решение с записью в реестре технического долга.

**Что не делаем:** не переписываем всю структуру БД «заодно». Только то, что блокирует сценарий.

---

### 5.6. Резервное копирование не настроено (риск)

**Решение:** настроить в первый день, до исправления БД.

| Действие | Описание |
|---|---|
| Ручная копия сейчас | Полная выгрузка БД в файл перед любыми изменениями |
| Автоматическая копия | Ежедневная выгрузка по расписанию, ночью |
| Хранение отдельно от БД | Копия хранится на другом носителе или в другом месте, чем сама БД |
| Глубина хранения | Не менее 7 последних копий |
| **Проверка восстановления** | Копия разворачивается на отдельной базе и проверяется. Копия, которую не проверяли, не считается копией |
| Дополнительная копия | Перед каждой миграцией структуры |

**Трудоёмкость:** 2–3 часа у разработчика БД. Это минимальная плата за закрытие риска, который иначе может стоить всего проекта.

**Ответственный:** разработчик БД. **Срок:** день 1, до 12:00. **Подтверждение:** тестировщик или руководитель присутствует на проверке восстановления.

## 6. Новая последовательность и параллельная работа

### 6.1. Старая и новая последовательности

```
БЫЛО (цепочка, все ждут Backend):
  БД ──> API ──> Интерфейс ──> Тестирование ──> Демонстрация

СТАЛО (параллельные треки, общая точка соединения):
  Трек 0 (день 1):   Резервное копирование ──> Миграция БД (дни 1–2)
  Трек A (Backend):  Контракт ──> API срезами (дни 3–8)
  Трек B (Frontend): Mock ──> Интерфейс на mock ──> Подмена на реальный API
  Трек C (QA):       Тест-кейсы ──> Тесты по контракту ──> Проверка сборок
  Трек D (аналитик): Контракт, сценарий демонстрации, коммуникация с заказчиком
                                   │
                    День 4–5: первое подключение реального API (срез «чтение»)
```

### 6.2. Что выполняется параллельно

| Одновременно | Кто | Условие |
|---|---|---|
| Резервное копирование и описание ошибки БД | Разработчик БД, аналитик | Копирование первым, описание параллельно |
| Миграция БД и подготовка контракта API | Разработчик БД и аналитик, Backend | Контракт опирается на целевую структуру |
| Миграция БД и работа Frontend на mock | Разработчик БД и Frontend | Mock не зависит от БД |
| Тест-кейсы и работа Frontend | Тестировщик и Frontend | Тест-кейсы пишутся по контракту |
| Разработка API и проверка предыдущих срезов | Backend и тестировщик | Срезы выкладываются поэтапно |

### 6.3. Что последовательно (нельзя ускорить параллелизмом)

| Порядок | Почему |
|---|---|
| Резервная копия → миграция БД | Без копии миграция недопустима |
| Миграция БД → реальные методы API на новой структуре | Иначе API придётся переписывать |
| Контракт API → mock-сервер → работа Frontend и QA | Mock строится из контракта |
| Реальный API (срез) → подмена mock → проверка тестировщиком | Нельзя проверить то, чего нет |

## 7. План по дням

День 1 это день контрольной проверки, день 10 это демонстрация заказчику.

| День | Руководитель | Аналитик | Backend | Разработчик БД | Frontend | Тестировщик |
|:---:|---|---|---|---|---|---|
| **1** | Решение по PDF, согласование с заказчиком; утверждение плана | Контракт API, сценарий демонстрации | Участие в контракте; планирование срезов | **Резервная копия и проверка восстановления**; описание ошибки | Участие в контракте; подготовка интерфейса к mock | Подготовка к проверке: список тест-кейсов |
| **2** | Контроль БД | Фиксация контракта (версия 1.0) | Первые методы чтения (на текущей структуре, только если не зависят от исправления) | Скрипт миграции, прогон на копии, **применение** | Интерфейс на mock | **Mock-сервер**; проверка данных после миграции |
| **3** | Контроль скорости Backend | Критерии приёмки сценария | Методы чтения на исправленной структуре | Тестовые данные, поддержка Backend | Интерфейс на mock, состояния ошибок | Тесты API по контракту |
| **4** | Контроль интеграции | Реестр изменений контракта | **Срез 1: чтение расписания** | Поддержка Backend | **Подмена mock на реальный API (срез 1)** | **Первая промежуточная сборка**: проверка |

## 9. Механизмы контроля

### 9.1. Ритм работы

| Мероприятие | Периодичность | Содержание |
|---|---|---|
| Синхронизация | Ежедневно, 10 минут | Сделано, будет сделано, что блокирует. Решения не принимаются, только фиксируются блокеры |
| Выкладка сборки | Ежедневно, до 16:00 (с дня 4) | Backend и Frontend передают сборку тестировщику |
| Результат проверки | Ежедневно, до конца дня | Тестировщик публикует список дефектов |
| Контрольная точка | По плану (раздел 8) | Проверка по критериям |
| Обновление реестра | Ежедневно | Блокеры, решения, изменения плана |

### 9.2. «Светофор» состояния

| Показатель | Зелёный | Жёлтый | Красный | Реакция на красный |
|---|---|---|---|---|
| Отставание Backend | до 1 дня | 1–2 дня | больше 2 дней | Сокращение сценария в тот же день |
| Простой участника из-за блокера | меньше 4 ч | 4–8 ч | больше 8 ч | Руководитель снимает блокер лично |
| Критичные дефекты | 0 | 1–2 | 3 и больше | Остановка новой разработки до исправления |
| Изменения контракта API за день | 0 | 1 | 2 и больше | Заморозка контракта, пересмотр с руководителем |
| Дней без сборки у тестировщика | 0–1 | 2 | 3 и больше | Передача любой работающей сборки немедленно |
| Резервная копия | свежая (до 24 ч) | старше суток | отсутствует | Остановка изменений БД до создания копии |

### 9.3. Правила управления изменениями

1. Любой запрос на изменение объёма фиксируется письменно.
2. Руководитель оценивает влияние на сроки и отвечает: что убирается или переносится взамен.
3. Принять без компенсации можно только то, что укладывается в резерв.
4. С дня 8 новые функции не принимаются.
5. Заказчик получает ответ на запрос в течение одного рабочего дня.

### 9.4. Правила эскалации

| Ситуация | Кто решает | Срок |
|---|---|---|
| Блокер между двумя участниками | Двое между собой | 4 часа |
| Блокер не снят | Руководитель | В тот же день |
| Изменение сроков или объёма демонстрации | Руководитель, затем заказчик | В течение дня |
| Потеря данных или сбой БД | Руководитель, немедленно | Сразу |

## 10. Итог

**Что было:** четыре проблемы и два риска, которые тянули друг друга: ошибка в БД и отставание Backend останавливали Frontend и тестирование, а новый запрос заказчика и отсутствие резервной копии угрожали добавить ещё больше сложностей.

**Что решено:**

| Обстоятельство | Решение |
|---|---|
| Backend отстаёт на 3 дня | Сокращение объёма до демонстрационного сценария, API вертикальными срезами |
| Frontend не может подключиться к API | Контракт на день 1, mock-сервер на день 2, подмена на реальный API по срезам |
| Тестировщик без сборки | Работа на mock с дня 2, промежуточная сборка с дня 4, ежедневная выкладка до 16:00 |
| Запрос на экспорт в PDF | Исключён из текущего плана; предложен перенос или облегчённая печатная форма при условии на день 7 |
| Ошибка в структуре БД | Исправляется в первые 2 дня, только в части, блокирующей сценарий, после резервного копирования |
| Нет резервного копирования | Настраивается в день 1 до любых изменений, с проверкой восстановления |

**Порядок приоритетов:** резервная копия, затем исправление БД, затем контракт API, затем всё остальное параллельно.

**Контроль:** десять контрольных точек, ежедневная выкладка сборки, «светофор» с готовой реакцией на красный сигнал, заморозка функций с дня 8.

**Главная мысль:** при отставании в три дня и десяти днях до показа спасает не скорость, а порядок и объём. Сначала защитить данные, затем убрать причину цепочки блокировок, затем сократить сценарий до того, что точно можно показать.
